# TSGColAgent 技术文档

## 1. 方法定位

TSGColAgent 是一种面向自动化单元测试生成的测试状态引导多智能体协作方法。

它的核心并不是把大语言模型直接接到测试代码生成器上，而是建立一个能够持续描述“程序结构、测试意图、执行结果、行为观察和质量变化”的测试状态模型，并以该模型作为多智能体协作的共同工作空间。
在传统的大模型测试生成流程中，模型通常根据源码一次性给出测试，后续只依据测试是否运行成功进行判断。这种方式难以区分“代码被执行”与“行为被验证”，也难以解释下一轮测试为什么要增加某个输入或修改某条断言。
TSGColAgent 将测试任务表示为一个持续演化的状态转换过程：源码分析得到初始测试状态，测试运行产生新的状态信息，状态变化再驱动下一轮测试目标和智能体选择。
因此，LangGraph 在本方法中承担的是流程编排和可恢复运行底座；TSG 的核心价值在于测试领域状态的组织方式、状态更新规则、目标选择逻辑和候选比较逻辑。两者分别解决“如何运行协作流程”和“协作流程依据什么做决定”这两个问题。

## 2. 总体技术架构

系统由五个层次组成。最底层是 Python 与 Java 的源码分析和测试工具链；其上是统一的结构化程序表示和测试状态模型；第三层是多智能体协作与任务规划；第四层是结果持久化、批处理和实验度量；最上层是实时监控台与测试知识交互界面。

实现采用 Python 3.11 作为后端基础，使用 Python AST 分析 Python 源码，使用 Tree-sitter Java 分析 Java 源码；
使用 LangGraph StateGraph 编排非线性流程，使用 SQLite 保存工作流检查点；
使用 pytest、coverage.py 和自研 AST Mutation Runner 完成 Python 测试执行，使用 JUnit 5、Maven/Gradle、JaCoCo 和 PIT 完成 Java 测试执行；
使用 Ollama 或 OpenAI 兼容 HTTP 接口提供可选的模型能力；
使用 React、TypeScript、Vite、Fetch 和 EventSource 实现实时实验台。

系统的关键技术链路如下：

```text
源码解析
  -> 统一程序表示
  -> 测试状态初始化
  -> 状态引导的任务规划
  -> 多智能体协作生成测试
  -> Python/Java 工具链执行
  -> 运行观测与质量计算
  -> 测试状态更新
  -> 定向生成、修复或结束
```

## 3. 测试状态引导机制

TSG 的基本抽象是测试状态模型，而不是单次测试报告。`core/structured_context.py` 定义了统一的源码上下文，包括模块、包、类、接口、枚举、记录、函数、构造器、参数、分支、循环、调用、返回和异常等对象；`graph/state_graph.py` 负责将这些对象与测试用例、断言、执行过程、运行时类型和变异结果统一保存。
程序结构与测试运行结果通过关系连接起来。源码定义关系形成程序结构，测试用例与函数之间通过执行关系关联，断言与运行状态之间通过观察关系关联，运行时类型通过类型流关系关联，变异体与测试之间通过杀死或存活关系关联。
这样，系统可以在同一个测试状态模型中回答三个层次的问题：哪些程序位置被触达，哪些行为被实际检查，以及测试是否能够区分程序行为变化。
每次源码分析、测试生成、测试运行、覆盖率采集、变异分析和修复都会形成状态事件。事件记录发送方、接收方、相关程序位置、运行轮次和具体载荷，并追加到状态模型的历史中。状态模型同时保存版本、执行轨迹、历史快照和当前元数据，因此可以按照任务轮次恢复，也可以在候选修改失败时回到之前的有效版本。
TSG 引导的关键在于根据状态变化构造下一项任务。系统不是固定执行“先覆盖、再断言、再变异”的流水线，而是从当前状态中判断最值得处理的方向。
例如，某个函数已经被运行但没有有效行为观察时，下一步应当生成更具体的断言；某个分支未被触达时，应当构造区分分支条件的输入；某个变异体存活时，应当寻找能够区分原始实现和变异实现的测试行为。

## 4. 源码理解与统一中间表示

Python 分析器通过 AST 遍历函数、类、异步函数、生成器、导入、分支、循环、返回和抛出语句，并根据参数注解、参数命名和函数体中的操作推断输入类型。
Java 分析器优先采用 Tree-sitter Java 语法树，读取类、接口、枚举、注解、记录、泛型、继承、重载、Override、方法参数、返回类型、分支、循环和异常。解析失败时，Java 分析器使用结构化正则降级路径保留基本方法和类信息。
两种语言的分析结果都会经过 `ContextRewriter` 归一化，形成统一的 `StructuredContext`。`StructuredGraphBuilder` 再将上下文转换为测试状态模型：类和方法成为程序结构节点，参数和返回类型成为类型相关节点，分支和循环成为控制流节点，调用、返回和异常成为行为节点。
构建阶段还会写入上下文提取和初始模型建立事件。这一层相当于系统的中间表示。上层测试生成器不需要直接面对 Python AST 和 Java Tree-sitter 节点，而是使用统一的函数名称、参数信息、控制结构、返回行为和异常行为。
下层执行器也可以把 Python coverage、AST Mutation、Java JaCoCo 和 PIT 的结果转换成相同的测试状态更新格式。

## 5. 多智能体协作与任务规划

TSGColAgent 的多智能体体系由测试状态决策、测试生成执行、知识学习以及覆盖增强、断言增强、变异增强、边界异常、运行时类型、测试有效性和 Oracle 修复等专项能力共同组成。它们不是互相独立的聊天机器人，而是通过测试状态模型和结构化任务包协同工作。
测试状态智能体负责分析当前测试状态、判断任务是否已经具备继续运行的条件、综合运行结果计算质量状态，并要求规划器生成下一步任务。
测试生成智能体负责把任务包转化为测试代码、执行工具链、收集运行结果并实施测试修改。
知识智能体负责读取历史任务经验、提供适用的生成策略和失败规避信息，并在任务结束后学习新的输入模式、断言模式和修复模式。

`orchestration/test_workflow.py` 使用 LangGraph 将这些协作动作编排成条件图。
流程节点包括源码分析、测试初始化、测试状态重建、知识检索、测试生成与运行、运行收尾、状态评价与重新规划、知识更新等。
路由条件由当前状态字段决定，因此可以在源码分析失败时转向重建，在候选执行失败时转向修复，在质量不足时转向专项优化，在质量满足目标或预算耗尽时结束。
LangGraph 的 `TestWorkflowState` 只保存当前任务的控制变量、任务计划、报告和路由信息；完整模型由 `SharedGraphMemory` 写入 JSON，工作流节点检查点由 SQLite 保存。
这样的分层既保证工作流可以恢复，又避免在每次节点跳转中重复复制大量源码结构和运行数据。

## 6. 测试生成方法

Python 测试生成使用结构化 `TestPlan` 作为模型输出和代码生成之间的中间层。
测试计划包含目标函数、输入参数、Oracle 类型、预期值、关联的程序位置、理由和置信度。
模型只负责提出结构化计划，计划解析器负责检查目标函数是否真实存在、Oracle 是否支持、置信度是否合法以及预期是否属于可执行形式。
模型生成的输入和预期值还会经过真实目标函数校准。
系统会在隔离子进程中执行模型提出的字面量输入，读取真实返回值或异常，把结果重新写入测试计划。
模型不可用或模型计划无法通过解析时，系统使用确定性生成策略，根据参数类型、文档字符串、源码操作和控制结构构造普通值、空值、边界值、成对分支值和异常输入。

测试代码由 `TestPlanRenderer` 统一渲染。它负责目标模块动态加载、包路径处理、类方法调用、异步函数调用、生成器展开和 pytest fixture 生成。
Java 测试生成器根据结构化方法信息生成 JUnit 5 测试。它根据静态方法、实例方法、返回类型和参数类型生成调用表达式，并优先生成具体返回值、边界值、集合值、字符串值和异常类型断言。
模型生成 Java 测试时必须保留包名和测试类名，且生成结果仍要交给 Maven/Gradle、JUnit、JaCoCo 和 PIT 的真实工具链确认。

## 7. 测试执行与多阶段评价

候选测试首先在临时目录中进行语法解析、编译、测试收集和测试运行。只有测试文件能够被框架收集、能够真实调用目标代码并且出现正常行为断言，才会进入覆盖率和变异评价。测试可用性分析会识别异常专用测试、弱断言、恒真判断、None 比较和只检查对象存在等情况。
Python 执行链由 pytest、coverage.py、运行时观察和 AST Mutation 组成。coverage.py 提供执行行、缺失行、执行分支和分支总数；运行时观察器从测试中抽取字面量目标调用，在子进程中记录返回类型、参数类型和异常类型；Mutation Runner 对比较、算术、布尔、一元和常量表达式进行变异，并逐个执行变异体。
Java 执行链由 JUnit 5、JaCoCo 和 PIT 组成。Java 工具链根据项目构建文件自动选择 Maven 或 Gradle，运行测试并解析 JaCoCo 报告；只有测试通过且覆盖结果稳定时，才进入 PIT。Java 子进程支持超时和进程树清理，使用隔离工作区避免无关类编译失败污染当前任务。
执行结果会被转换为统一的运行报告，报告包含测试是否通过、收集数量、正常行为测试数量、断言总数、有效断言数量、行覆盖、分支覆盖、状态流覆盖、变异分数、运行时观测、超时原因和测试失败分类。评价模块由这些结构化数据和测试状态模型共同完成，而不是仅依赖 pytest 返回码。

## 8. 定向修复与质量优化

测试失败后，`PytestFailureClassifier` 会区分语法、导入、收集、fixture、Oracle、运行时和超时问题。状态模型还会记录失败测试、关联程序位置和当前运行轨迹。`GraphQuery` 根据未访问程序位置、存活变异、缺少断言的函数、未覆盖异常和未知运行时类型生成可执行的优化方向。

`GraphDefectPropagation` 沿程序结构和测试关系传播质量问题，较强的观察、修复目标和存活变异关系会产生更高的传播权重。`StatePositioningRepairStrategy` 根据失败信息决定修改范围，优先定位到断言、测试方法或局部代码，而不是直接重写整份测试。

`RootCauseRepairPlanner` 会从传播结果中选择根因函数，并根据实际目标运行结果生成最小补丁。

候选补丁由 `PatchSearchRepair` 放入临时测试环境重新运行。系统比较补丁前后的测试通过情况、行覆盖、分支覆盖、状态流覆盖、断言有效性、变异结果和综合质量。

如果补丁造成已有指标下降、没有产生可测量提升或只有弱断言变化，就保留原测试。对于模型返回的修复操作，`TestRepairOperationApplier` 只允许添加、替换或删除指定测试函数，并在最终写入前再次进行补丁评价。

## 9. 质量模型与实验度量

断言有效性 AE 由断言具体性、正常行为比例、断言与运行状态的关联程度和断言类型多样性组成，权重分别为 0.45、0.25、0.15 和 0.15。只有存在正常行为断言时，异常断言才不会独占 AE。

`Thresholds` 将结果分为可用、可接受和高质量状态，并检查测试通过、测试收集、正常行为、有效断言、覆盖率和可靠变异样本。批量任务还会保留 A/B/C/D/E 等级、轮次轨迹和失败原因。该等级用于批处理的恢复与优化调度，具体指标仍保存在任务级报告和 `paper_metrics` 目录中。

`metrics/measurement.py` 为每个任务记录工具级运行会话、测试开始数量、Java 报告变化、耗时和源码哈希。`metrics/paper_metrics.py` 独立计算 PassRate、AvgExec、TIR、覆盖率、AE 和 Mutation 等实验指标，缺少数据时保留为 None。实验统计与运行时任务选择分离，避免把分析指标反向混入生成策略。

## 10. 知识学习与长期经验

`AgentExperienceMemory` 将每次任务的结构特征、目标语言、分支和循环数量、参数类型、操作符、动作、失败类别、前后质量变化和运行成本保存为经验记录。检索时综合语义相似、任务结构相似、历史收益和时间衰减，返回成功策略、失败模式、低收益模式和可操作提示。

长期知识既支持批量任务之间复用，也支持监控台对话。测试知识智能体可以从实验结果回答确定性问题，也可以从测试方法问题中提炼候选概念。对话产生的概念先处于学习状态，只有真实任务采用该概念并产生多次成功结果后，才会成为稳定知识。批量轮次可以隔离任务日志，并通过 merge ID 将经验安全合并到长期知识库。

## 11. 批量实验、持久化与监控平台

批量入口根据源码目录、语言和任务规模选择并行策略。Python 任务可以并行处理，但模型请求受到信号量限制；Java 类级任务使用独立工作区，避免多个类共享编译和报告目录。每个任务单独保存测试文件、测试状态模型、工作流检查点、质量报告、失败报告和运行时信息，批量层再汇总数据集级结果。

系统通过源码文件签名、源码哈希、摘要状态和任务轮次判断哪些任务可以跳过，哪些任务需要重新生成，哪些失败任务应直接进入恢复轮次。优化失败时，系统恢复此前最佳测试。任务运行时间按实际运行区间累计，不把进程重启或机器空闲时间误算为测试耗时。

监控后端使用 Python 原生 HTTP 服务实现实验登记、任务队列、运行快照、事件流、报告读取、知识问答和对话存储。

前端使用 React/TypeScript/Vite，通过 Fetch 获取快照，通过 EventSource 接收实时事件。实验总览、智能体协作、阶段运行、测试状态、任务报告、知识库和系统信息均来自后端统一的 RuntimeSnapshot 数据结构。

## 12. 技术特点与适用边界

TSGColAgent 的主要技术特点是将测试生成从一次性代码合成提升为测试状态驱动的多智能体协作过程。大语言模型负责提出候选方案，但源码分析、结构化计划、真实工具执行、状态更新和质量评价决定候选能否继续流转。没有模型时，系统仍可通过结构化分析、确定性输入和工具链完成基本测试生成。

系统同时具备统一中间表示、跨语言执行适配、可恢复工作流、状态目标优化、长期经验学习和实时实验观测能力。Python 和 Java 虽然使用不同的解析器和测试工具，但最终都被转换为相同的测试状态更新、运行报告和质量评价接口。

Java 质量评价依赖本机 JDK、Maven/Gradle、JaCoCo 和 PIT；模型能力依赖 Ollama 或 OpenAI 兼容服务。

从技术架构角度看，TSGColAgent 其核心价值不在于增加某一个生成模型，而在于让多个智能体围绕统一的测试状态持续协作，并把每一轮生成行为与程序结构、运行行为和质量变化关联起来。
